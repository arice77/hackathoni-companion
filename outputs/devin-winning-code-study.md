# What Player Two and Mulligan actually verified

**Design decision for a multilingual desktop helper.** Keep the spoken support task and the engineering repair on separate clocks. Let the user ask in Malayalam, hear the interpreted action, approve it, and see the resulting screen or saved record. If the helper encounters a product defect, offer to file a reproducible case for a repository the team controls. A repair can continue after the conversation ends. Player Two’s best-documented run took roughly seven minutes after approval. Mulligan shows how to preserve the state of one action so a later human edit survives a reversal. ## Player Two · From a visual finding to a verified game repair

1. **Establish the defect before spending a Devin session.** Holo reports its observations. `Verifier.verify_demo` replays the game engine’s recorded inputs and judges them against a hidden event log. The orchestrator stops the repair path when the finding remains suspected. The live fix path also requires a recognized bug with a registered replay script. General desktop apps need their own equivalent, such as an expected receipt, a saved field or an application status that a separate check can read. [Verifier](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/agents/verifier.py#L142-L167) · [Finding gate](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/app/orchestrator.py#L355-L385) · [Supported replay cases](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/app/orchestrator.py#L683-L699)
2. **Bind approval to one case.** The orchestrator clears stale “fix it” utterances before presenting each case and discards voice approvals heard during its own narration. It can wait for a fresh button or voice decision. There is also a separately configured auto-fix mode. In the measured live run the user pressed **Fix**. In that path the one click authorizes the first merge onto the isolated QA branch. A follow-up PR stays open. A desktop helper promising review of the actual diff needs its own approval *after* the PR appears. [Intent handling](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/app/orchestrator.py#L355-L404) · [Single-merge approval](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/app/orchestrator.py#L697-L719) · [Actual input](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/eval/runs/2026-11-08-stage-live-loop-fixed.json#L20-L26)
3. **Open a bounded session, then show progress.** The server builds a prompt with the finding ID, repository, base branch, steps, expected and actual behavior, and a log excerpt. Its v3 organization client posts the prompt with a repo list, tags and a default 10-ACU ceiling. It retains the returned session ID and URL. Polling defaults to 15 seconds and a one-hour limit. It reads PR state and ACUs from the session and handles queued, working, PR-open, merged and failed states. A PR link gives the user something to inspect while CI runs. Session creation needs working organization credentials and repository access and consumes the applicable plan allowance or credits; the inspected code does not establish what a particular account can use for free. [Case payload](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/devin/client.py#L36-L55) · [Session creation](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/devin/client.py#L101-L172) · [Status mapping](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/devin/client.py#L69-L91) · [Polling](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/devin/client.py#L180-L245) · [Cognition authentication](https://docs.devin.ai/api-reference/authentication)
4. **Merge, rebuild and independently check the same condition.** Once approved, the client sends a message asking Devin to squash-merge the PR into the case branch; the loop then waits for the API to report a merge. It rebuilds from `pull/N/head` when available. On Windows it resolves the PR head SHA and waits for its CI artifact, with a 20-minute default build wait. The QA script checks the output event stream. A crash, timeout or empty log cannot pass. One further feedback round is possible. For a desktop app, verify the exact revision the user will run and require positive evidence that the previously failing step was exercised. **What happened on stage.** The team published a November 8 summary of a *live dashboard run with a supplied test plan*, transcribed from the stage machine. The agent reported an invulnerability rendering defect. The user pressed Fix, Devin opened a PR, the PR merged, and the after-fix replay logged the power-up and zero occurrences of the visual defect. The PR independently identifies the Devin bot and the actual code change. The summary reports **438 seconds** from approval to verified repair; its printed UTC endpoints imply **441 seconds**. The PR appeared approximately **129 seconds** after approval. These are observations from one run. The raw recording directory stayed on the stage machine. [Run summary](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/eval/runs/2026-11-08-stage-live-loop-fixed.json#L1-L29) · [Merged game PR and before/after evidence](https://github.com/kaktamsdengami/chocolate-doom/pull/4)

The **blind** run was separate: it produced four findings and verified one wall-rendering issue. Another earlier demonstration rebuilt a sky-bug finding from its text and fixture logs, started Devin from a VM and stopped at an unmerged PR. A cached-build code path can replay a previous fix, labeling it as earlier work. Keeping these paths distinct matters when a live stage demo has little time or poor connectivity. The evidence supports one successful end-to-end repair and does not establish a general detection rate. ## Mulligan · Bound an agent’s actions and check the resulting state

**Where Devin fits.** Mulligan is a gateway that agents call through MCP. The source authenticates each tool caller, binds it to a session and exposes typed operations such as updating selected rows or closing a chosen issue. The gateway owns the downstream credentials. The optional Devin connection is a bearer-authenticated HTTP MCP server configured in Devin. A sessionless client can reuse a session by agent token until an idle timeout, so a concurrent multi-user app should explicitly bind user, support case and action. Actions performed outside this gateway need their own audit trail. [Token and session binding](https://github.com/Manas-33/mulligan/blob/e0c7850605e5c41e2aab8db7a9635c1f27e1f215/gateway/mulligan/mcp_server/server.py#L43-L74) · [MCP dispatch and typed inputs](https://github.com/Manas-33/mulligan/blob/e0c7850605e5c41e2aab8db7a9635c1f27e1f215/gateway/mulligan/mcp_server/server.py#L139-L212) · [Devin connection](https://github.com/Manas-33/mulligan/blob/e0c7850605e5c41e2aab8db7a9635c1f27e1f215/README.md#L174-L178)

**How a tool call becomes verifiable.** The gateway records a pending action, then classifies it before invoking the adapter. Held actions carry a concrete ID and await a decision. For eligible writes the adapter captures the prior values, performs the call, captures the outcome and builds an inverse. It saves the action under a per-system lock, including field hashes, so a later rewind can identify changes that belong to another user. A call whose remote outcome is uncertain can retain evidence for reconciliation. [Pending and held calls](https://github.com/Manas-33/mulligan/blob/e0c7850605e5c41e2aab8db7a9635c1f27e1f215/gateway/mulligan/core.py#L210-L266) · [Capture, execute and inverse](https://github.com/Manas-33/mulligan/blob/e0c7850605e5c41e2aab8db7a9635c1f27e1f215/gateway/mulligan/core.py#L300-L369) · [Approval decision handling](https://github.com/Manas-33/mulligan/blob/e0c7850605e5c41e2aab8db7a9635c1f27e1f215/gateway/mulligan/holds/manager.py#L124-L191)

**How undo earns its verdict.** The rewinder waits for in-flight actions, applies supported inverses and compares the expected and observed state for each system. Unknown upstream calls can be skipped and a step can fail without being reported as restored. The seeded tests replay sequences of Postgres changes against a reference checksum and independently cover a human editing a field before reversal. An original desktop helper can use the same idea for one supported action: remember the record’s ID and prior value, apply a change, read it back, then reverse only fields still carrying the helper’s write. [Rewind and verification](https://github.com/Manas-33/mulligan/blob/e0c7850605e5c41e2aab8db7a9635c1f27e1f215/gateway/mulligan/orchestrator/rewind.py#L291-L378) · [Randomized test](https://github.com/Manas-33/mulligan/blob/e0c7850605e5c41e2aab8db7a9635c1f27e1f215/gateway/tests/test_undo_fuzz.py#L401-L436) · [Human-edit test](https://github.com/Manas-33/mulligan/blob/e0c7850605e5c41e2aab8db7a9635c1f27e1f215/gateway/tests/test_undo_fuzz.py#L497)

**What the evidence supports.** The team credits Devin with the randomized tests and three verification fixes. PR #17 is a merged change under Manas Dalvi’s GitHub account. Its description gives 50 default seeded sessions and the three specific failure cases. The 200-action load script repeatedly updates rows in one local Postgres table, times the rewind separately and requires matching checksums in under 30 seconds. That does not measure 200 cross-service actions or hosted Devin latency. The live demo runner invokes Anthropic, and a recording can drive the deterministic fallback. The team’s submission claims Devin-client support; an earlier SDK note still marked the live Devin tool-call check as pending. I found implementation and setup evidence, but no independently verified live Devin round-trip in the inspected run evidence. ## Applying the findings to a Sarvam + Devin desktop helper

| Step | What the user sees | What the team verifies |
|---|---|---|
| Hear the request | The original-language transcript, a brief interpretation and the proposed action. | Test Malayalam, English and mixed speech against fixed cases. An ambiguous name, account or amount gets a clarification. |
| Perform one action | The user confirms the exact target and sees the result. | Read back the expected value or receipt from the owned demo app. Store a case ID, the action, old/new state and the checked result. |
| Escalate a defect | On a failed, repeatable check, offer a case containing the steps and expected/observed result. | Use one team-owned repo configured for Devin. Keep service credentials server-side. Persist a single case-to-session mapping before a repeated press can create a second paid job. |
| Show the repair | The PR and CI status stay visible while the user continues. After review, show the same failing case against the corrected revision. | Record the baseline failure, exact commit, positive success condition and negative check. Maintain a clearly dated recording for judge sessions shorter than the real repair. |

These are proposed adaptations. Player Two supplies the case/replay and asynchronous repair evidence. Mulligan supplies the typed actions and state checks. Sarvam’s voice layer and an independent desktop UI would be new engineering work. [Player Two live repair](https://github.com/kaktamsdengami/player-two/blob/84a947382abd6ee04226b027b3fcf823960f6808/app/orchestrator.py#L683-L723) · [Mulligan checks](https://github.com/Manas-33/mulligan/blob/e0c7850605e5c41e2aab8db7a9635c1f27e1f215/gateway/mulligan/orchestrator/rewind.py#L352-L378)

**Dependencies and reuse.** Player Two declares Python 3.12+, FastAPI, httpx and H’s desktop-agent SDK. Its demonstration also relies on a supported game build and authenticated GitHub access to create a branch and read CI artifacts. Mulligan’s gateway pins Python 3.12, FastAPI, the MCP SDK, psycopg and Sentry, among others. The public snapshots contain no top-level product license and GitHub reports no detected repository license for either. Player Two separately credits Chocolate Doom under GPL-2.0 and Freedoom under BSD-3-Clause. The engineering patterns above can be independently implemented. This study inspected public GitHub code and run records without cloning these two repositories, installing dependencies, running their apps or making paid calls.
